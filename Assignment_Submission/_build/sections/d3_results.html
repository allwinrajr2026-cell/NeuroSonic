{{t-det}}, {{f-lat}} and {{f-qual}} summarise the comparison. RF-DETR Nano had the best AP and recall. Recall matters most for a warning system because a missed person is worse than an extra caution. Its 21 ms GPU latency fits a 200 ms frame interval and its licence is permissive. The YOLO26 models are faster but have lower recall and are AGPL-3.0. RF-DETR is too slow on the CPU (122 ms), so SSDLite remains the fall-back. RF-DETR's precision at 0.40 (0.588) is slightly lower than the others', so more false detections are expected; the temporal confirmation is designed to absorb them. On the same images, all four RGB detectors scored far above the WOAD checkpoint, which was trained on different scenes.

Person quality is unchanged in FP16 (AP@0.5:0.95 0.304 vs 0.305; precision at 0.40 0.588 vs 0.595). Back to back both take about 17 ms. At the application's 5 frames/s, however, the GPU drops to its lowest power state between frames (sampled clocks 210–405 MHz), and FP16 lowers the median from 66.5 to 53.2 ms and the p90 from 78.6 to 60.8 ms ({{t-fp16}}).

Serving efficiency at a fixed 5 frames/s

CPU threads. With RF-DETR on the GPU, PyTorch's default pool of 8 CPU threads kept the server at 712 % of one CPU core while streaming 5 frames/s, although the GPU did the detection. Two threads cut this to 121 % with no loss of frame rate ({{f-cpu}}); median frame times were 30, 38 and 25 ms for 8, 4 and 2 threads.

GPU power state. At 5 frames/s the GPU is idle about 90 % of the time. In repeated timings it dropped to its lowest performance state (P8, about 390 MHz); the same inference took about 16 ms at P5 (≈600 MHz) and about 74 ms at P8. This explains why live latency is several times the back-to-back benchmark. Inference thread. Running GPU inference from a fresh thread per request cost about 3 ms per call in isolation (19.4 vs 16.2 ms median), so all inference was moved to one long-lived thread.

Ten-minute soak tests

A soak-test tool streamed the clip to the server at 5 frames/s, one request at a time as the phone does, and every 60 s sent a parallel cloud request to a mock provider that takes 20 s. "Before" ran the earlier code (FP32, inference on request threads); "after" ran the final code.

Both runs were stable ({{t-soak}}, {{f-soak}}): no errors, a constant 4.97 frames/s, every slow cloud request answered while frames continued, and no growth in GPU memory. After the changes, latency was steadier (window medians 70–78 ms instead of 62–104 ms) and the worst p90 fell from 111 to 92 ms. Of the 148 events, 100 named the person and 48 the bicycle, which is correct for a person riding a bicycle. Ten minutes on one machine cannot exclude a slow leak over hours.

End-to-end behaviour in the browser

Seven headless-Chrome tests drive the real phone interface at iPhone size against the server, with the network blocked. In the event test the page achieved 4.91 frames/s at the recommended 200 ms interval; the capture-to-answer time measured in the page (JPEG encoding, HTTP on loopback, full server pipeline) had a median of 67 ms, p90 73 ms and maximum 81 ms over 44 frames. "Caution. A person is moving into your path from the left." was delivered, and the neural-voice audio started 257 ms later. In the slow-cloud test the phone said "Still waiting for the online description. Local walking guidance continues." at 15.2 s and spoke the description at 20.1 s, while 99 frames were analysed in the meantime. {{f-shots}} shows the interface.

Automated tests and quality gate

The suite runs 204 test cases (unit, integration and HTTP API tests, plus 32 Node tests of the browser logic): OK in the GPU environment (1 skipped: an opt-in live cloud test) and OK in the CPU-only environment (3 skipped: two GPU-only tests and the live test, with automatic fall-back to SSDLite). The 22 perception tests cover detector fall-back, recovery of a known camera shift and zoom, stable track identities while the camera pans, entering and crossing in both directions, the absence of events for a static car during a pan, a shaky camera, a blocked view, slow drift and chairs, and the absence of distance and safety words. All seven browser tests pass. A quality-gate launch with the documented command passed in both environments: frames, speech, place search, a 1330 m route with 10 steps, and a voice command. On 3 November 2026 the release launcher started the server as an independent background process, and its local-network HTTPS address (the one the iPhone uses) answered when checked from the laptop; the iPhone itself has not yet been connected for these tests.
