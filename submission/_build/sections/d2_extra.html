Procedure

  1. Isolate the original. The original repository was copied read-only; no file in it was changed, so every comparison is against the authors' code as published.
  2. Identify the checkpoint. The exp72 checkpoint was hashed (SHA-256 prefix da043ff2), its module tree listed and its dimensions read: eight transformer blocks, eight heads, model width 64, positional embedding 1×128×64, 7,521,992 parameters.
  3. Re-implement inference. Loader, preprocessing, non-maximum suppression and coordinate scaling were written as a standalone package with the original numerical behaviour.
  4. Prove equivalence. The original model code and the re-implementation were run in separate processes on identical seeded inputs; the outputs were identical.
  5. Test that the inputs matter. Input swapping and blanking (ablation) and deliberate preprocessing faults were added as automated tests.
  6. Audit the data. The published archive was downloaded and verified; classes, counts, duplicates and frame identity against the run's validation set were checked; the other download links were inspected through their archive indexes.
  7. Evaluate. Person AP was computed with the original matching and AP code, verified to be numerically identical to the original on random data.
  8. Probe the live-input path. A raw sensor recording was compared with the training-like data, and the effect of brightness on detections was measured.

Download links

Nine Google Drive links are listed in the repository. File names, sizes and dates were read with HTTP HEAD requests, and archive contents from each RAR5 archive's index with a few small HTTP range requests (validated by listing the downloaded dataset and comparing all 9,370 file sizes). The code bundle (1.70 GB) contains the YOLOv5 code, a third checkpoint of a different size, and the same images with labels only inside training caches. Two archives hold unlabelled NIR + depth sequences (600 and 501 frames), which are useful for qualitative replay. One archive holds the SDK binaries, others hold Android build files, the RL project and the FPGA files. One link is dead (HTTP 404). No link contains the labelled person/Ebike/Car data of the reported run.

Threats to Validity of the Re-implementation

  • Numerical precision. We evaluated in FP32 on the CPU; the original validation used FP16 on CUDA. The effect is expected to be negligible but was not measured.
  • Different data. The measured AP is cross-dataset. It shows weak generalisation to the published scenes, not an error in the authors' own validation. Whether some published images were in the run's training data cannot be checked; the low scores make large overlap unlikely.
  • Metric quirks of the original code. A perfect detector scores 0.995, not 1.0, with the original AP interpolation; and in the original confusion analysis unmatched detections are counted only in images that also contain a match, so false positives are under-stated. We kept these behaviours deliberately, to stay comparable.
  • Class mapping. Only person is semantically shared. Bicycles scored as "Ebike" (AP ≈ 0) are reported only as an exploratory observation.
  • Label anomalies. One orphan label and 53 file names reused across splits with different pixels; no image was excluded, following the original label rules.

Building on the Base Model: Alert Engine and Input-Quality Gate

To turn per-frame detections of the base model into spoken alerts for recorded sensor data, an alert engine and an input-quality gate were implemented around it. They are retained in the final system as its research "replay" path.

The engine confirms an object when it is seen in two of three consecutive frames, groups objects of the same class and position into one message (e.g. "Person detected ahead."), orders messages by class priority and box size, applies cool-downs, and announces when detection becomes unavailable or resumes. The quality gate compares each frame's NIR brightness and contrast and the fraction of invalid depth pixels with thresholds derived from the brightness experiment, and it withholds object alerts from "unusable" frames instead of speaking possibly meaningless detections. Both components are covered by automated tests. Their design principles (temporal confirmation, position words instead of distances, explicit "unavailable" messages) carried over into the phone-camera system.
